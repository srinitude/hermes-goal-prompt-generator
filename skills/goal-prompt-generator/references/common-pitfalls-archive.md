# Archived goal-prompt-generator operational pitfalls

These long-form gotchas were moved out of `SKILL.md` to keep the primary skill under Hermes' content limit while preserving the detailed operational history.

22. **Running Firecrawl in a background terminal session that loses `FIRECRAWL_API_KEY`.** Some terminal/MCP backgrounding paths spawn the child process without the parent's exported environment. Re-run banner-shaped files and explicitly carry the key into background invocations when needed. **Confirmed sub-case (May 2026): `mcp_execute_code` does NOT inherit fish `set -gx` global vars into the python child's `os.environ`, so `subprocess.run(..., env=os.environ.copy())` ships an envless child even when the user's interactive shell has the key.** Diagnostic: a 493-byte JSON file containing the interactive `Welcome! To get started, authenticate...` banner instead of a `{"success":true,"data":{"links":[...]}}` payload. Recovery: parse the key out of `~/.config/fish/config.fish` (`set -gx FIRECRAWL_API_KEY fc-...`) and inject it into the env dict before each `firecrawl` subprocess. Recipe in `references/research-tool-readiness.md` §"When the helper baseline says `auth: unavailable` but the live probe says authenticated". Also: prefer `subprocess.run(..., capture_output=True)` over `subprocess.Popen(..., stdout=open(file,'w'))` for `firecrawl map` — file-redirected Popen has reproduced the env-loss failure mode even when capture_output works in the same cell.
23. **Assuming `firecrawl scrape --format markdown --json` nests output under `data.markdown`.** Firecrawl 1.16.0 returns scrape JSON at the top level: `{"markdown": "...", "metadata": {...}}`. Map output is nested as `{"success": true, "data": {"links": [...]}}`. Two more scrape-specific quirks live in `references/firecrawl-cli-1-16-quirks.md` §3a–3b: (a) `firecrawl scrape ... --json > file` prepends a `Scrape ID: <uuid>` header line that breaks `json.load()` — use the regex strip in §3a; (b) a `firecrawl scrape` exit `0` with non-empty `markdown` can still be a 404 page — always check `metadata.statusCode == 200` before citing the scrape. Two map quirks live in §5a–5b: mapping `github.com/<org>/<repo>` returns 0 links (use `opensrc` for repo source instead), and `EHOSTUNREACH 35.245.250.27:443` is a transient edge blip that resolves with a 3-second sleep + retry. For `opensrc`, `path`/`fetch` may error on the GitHub API even when the repo is already cached — probe `opensrc list` first (see `references/research-tool-readiness.md`).
24. **Treating an apparently-contradictory user requirement as one to silently relax.** Honor both constraints literally and resolve the paradox via deterministic regeneration from in-tree templates; see `references/paradox-resolving-goal-prompts.md`.
25. **Soft-wrapping the Coding Agent Execution Contract paragraph or omitting any of the 19 required `claude` flags.** The validator (`validate_optimized_markdown`) substring-matches the `CLAUDE_CLI_EXECUTION_CONTRACT` constant and each individual flag (`--print`, `--add-dir`, `--agent`, `--allow-dangerously-skip-permissions`, `--dangerously-skip-permissions`, `--debug-file`, `--effort max`, `--include-hook-events`, `--output-format stream-json`, `--include-partial-messages`, `--input-format stream-json`, `--json-schema`, `--mcp-config`, `--settings`, `--strict-mcp-config`, `--system-prompt-file`, `--tools`, `--verbose`, `--worktree`). Wrapping the paragraph at ~80 cols silently invalidates the file. Keep the boilerplate paragraph on a single physical line and reproduce every flag exactly as listed. `--print` is the long form of the prompt-mode flag (the prompt itself is a positional argument, NOT the value of `--print`); `--strict-mcp-config` is a **boolean** that constrains MCP loading to `--mcp-config <file>`. The pre-1.6.1 contract literals `--p` and `--strict-mcp-config <mcp-json-file>` are rejected by the live binary. The companion YAML `coding_agent_execution_contract` block must mirror the same set under `required_flags[*].name`, and the `canonical_invocation` string must contain every flag. See `references/auditing-cli-flag-inventory.md` for the audit playbook and the official-source cross-check.
26. **Running the test suite under macOS system `python3` (Xcode framework Python) and getting `ModuleNotFoundError: No module named 'yaml'` from a deeply-nested subprocess.** The skill's `tasklist.py` imports `yaml`, and `test_built_in_and_shareable_outputs_match_for_software_prompt` shells out to a fresh `python3 -c …` that re-imports the package. If your interpreter doesn't have PyYAML on `sys.path`, the failure surfaces as a `subprocess.CalledProcessError` deep inside pytest's traceback, not as the underlying ImportError. Fix: create a one-shot venv inside the skill dir (`/opt/homebrew/bin/python3 -m venv .venv && .venv/bin/pip install -q pyyaml pytest`) and run `.venv/bin/python -m pytest`. Delete the venv afterward — don't commit it. Do NOT chase it as a code bug; the test is fine, the interpreter is the problem.
27. **Mistaking DNS-blocked research tools for provider-specific or Hermes blocking.** If Firecrawl/opensrc fail after initially working, or multiple developer/AI sites such as GitHub and Hugging Face are blocked, run the non-mutating DNS matrix in `references/dns-blocked-research-tools.md` before blaming Hermes, Firecrawl, opensrc, or a single provider. Record completed maps separately from failed scrape/extract/fetch attempts, and preserve unavailable source/doc validation as execution-time required evidence instead of claiming success.
28. **Fabricating Firecrawl `extract` or `crawl` evidence because the contract names the full toolset.** Firecrawl CLI 1.16.0 has no top-level `extract` subcommand and small `crawl --wait` jobs can time out even when map/scrape/search work. Probe `firecrawl --help` first; route schema-driven extraction through `firecrawl agent --schema-file <path> --urls <url[,url...]>`. If a tool returns no usable output, record an honest attempted/unavailable evidence entry and preserve execution-time validation rather than fabricating extract/crawl evidence. See `references/firecrawl-cli-1-16-quirks.md` §6a–6b and `references/contrarian-validation.md`.
29. **Letting helper-generated handoff text drift from the skill's canonical handoff contract.** If the printed `/goal` line omits a required reference such as `principle_ids`, patch the helper source (currently `src/goal_prompt_generator/tasklist.py::handoff_prompt`) and then run `scripts/validate_skill.py` plus the Markdown/YAML validators before reporting completion. Do not only hand-edit the chat line; future generator runs must emit the corrected contract automatically.
30. **Assuming the host-side skill helper path is mounted into a remote terminal backend.** In Daytona/remote-backend sessions, `/Users/kiren/.hermes/skills/...` may be visible to `skill_view()` but absent from the executable backend filesystem. Probe the helper path first. If missing, use `skill_view()` to load scripts/templates/references and reconstruct the generation flow in `~/.hermes/goal-prompts/` with local validators, minimal dependency installation, honest Firecrawl/opensrc unavailability evidence, and the same final `/goal` handoff contract. See `references/remote-backend-helper-unavailable.md`.
31. **Burning three `mcp_patch` retries on the post-write verifier's 1-byte-trailing-newline flake before switching strategies.** When patching a generated goal Markdown file or the helper source itself, `mcp_patch` / file patching (replace mode) can return `success: false` with `wrote N chars, read back N+1` even though the patch landed correctly on disk — confirmed by `wc -c` + `grep` / `read_file` on the file. The same false-negative can happen on skill helper files such as `constants.py` or `validate_task_list_yaml_contract.py`, not just generated Markdown. Pre-empt it: after the FIRST failure, re-read the file; if the new content is present, treat the verifier as flaky and switch to a single `mcp_execute_code` pass with a `[(old,new), ...]` list of replacements or continue from the verified on-disk content. Do not retry the same patch three times. This is also the right pattern any time you need 5+ section rewrites on a generated Markdown — it's faster, gives explicit per-anchor MISSING reporting, and avoids the loop warning entirely. See `references/programmatic-yaml-rebuild.md` for the full pattern (and for the matching "rewrite the YAML from a Python dict, don't patch it" workflow).
32. **Fabricating runtime/source evidence while retargeting an existing goal.** When the user asks to make a new environment (for example Daytona) the real source/runtime location, patch the existing Markdown/YAML in place and validate both files, but do not invent tool baselines from upstream source and do not start executing the goal. Probe the new canonical paths/tools, mark only the relevant readiness task blocked if missing, and record exact blockers/resume points. See `references/retarget-existing-goal-runtime.md`.
33. **Letting requirements dribble in across multiple turns instead of probing for them up-front.** A single user message saying "Use Firecrawl on docs.railway.com and opensrc on Railway repos" is almost always followed by 2–4 more messages adding more sources, switching execution backends, or demanding additional validation passes. If you start the generation pass on just the first message, you will rebuild the YAML and re-run validators every time a new requirement arrives. Pre-empt this in the first turn: if the user names a docs site or one repo, ask `mcp_clarify` whether they also want (a) docs for the *consumer* of that source (e.g. Hermes itself when the goal is a Hermes backend), (b) every related open-source repo from the same org, (c) a runtime-environment switch (Daytona→local, etc.) before validation, and (d) any explicit parity invariants like "complete parity with X". Capture all of those in one structured clarification before writing artifacts.
34. **Claiming Firecrawl is `auth: authenticated` when only the API key parsed.** `firecrawl --status` exits 0 and prints `Authenticated via FIRECRAWL_API_KEY` purely from env-var parsing, before any HTTP request. If the actual `firecrawl map` / `scrape` calls return `Error: read ECONNRESET` or `curl: (35) Recv failure: Connection reset by peer` against `api.firecrawl.dev` (35.245.250.27:443), the correct YAML state is `auth: unavailable` with the requirement under `execution_time_required[]` — NOT `auth: authenticated` with empty `required_maps_present: {}`. The structural validator rejects the latter combination. Distinguish the L7-RST failure mode (TCP handshake succeeds, TLS layer is reset, retries are persistent) from §1 (DNS not resolving) and from `firecrawl-cli-1-16-quirks.md` §5b (transient `EHOSTUNREACH`). See `references/dns-blocked-research-tools.md` §3 for the probe pattern. The CRITICAL companion fix lives in `src/goal_prompt_generator/research.py::_firecrawl_auth()`: when `--status` reports BOTH `Authenticated` and any of `Could not fetch`, `fetch failed`, `ECONNRESET`, or `Connection reset` in the same banner, downgrade to `unavailable`. Without that downgrade, generating a fresh goal Markdown with the env key set writes `auth: authenticated` + empty `required_maps_present`, which the YAML validator rejects on the next call — turning every helper run with the user's API key set into a self-inflicted contract violation.
35. **Re-typing the same source-claim assertions across runs instead of using `scripts/validate_source_claims.py`.** Every generation pass that names ≥1 opensrc repo and ≥1 cited file path SHOULD pre-flight those claims with the deterministic verifier. The script offers a `Verifier` class with `opensrc_repo(slug, key_paths)`, `file_substring(path, needle)`, `tcp_reachable(host)`, `tls_reachable(host)`, `firecrawl_usable()`, and `helper_present(path)`. Import directly: `sys.path.insert(0, '<skill-dir>/scripts'); from validate_source_claims import Verifier; v = Verifier(); v.opensrc_repo(slug, key_paths)`. `opensrc_repo` expects the slug shape `<org>/<repo>` (NOT `github.com/<org>/<repo>`); returns a **bool**, not a dict — call `v.report()` for pass/fail counts, `v.failures`, `v.notes`. The script has docstring usage examples but no `__main__`. Two macOS host gotchas: `opensrc_repo` hardcodes `/root/.opensrc/repos/...` (Daytona/remote-backend path) and reports false `no main/ or master/ dir` when the cache is at `/Users/<user>/.opensrc/repos/...`; confirm by hand with `ls /Users/$USER/.opensrc/repos/github.com/<slug>/main/` and treat a failed `opensrc_repo` check as inconclusive on macOS. `firecrawl_usable()` is over-aggressive on a clean host with no `.firecrawl/` cache directory — trust the live `scripts/probe_firecrawl_reachability.py` (it does a real `firecrawl map` and checks `data.links` populated) over the banner-parser, and record both verdicts honestly in `validation_evidence.firecrawl.evidence[]`.

36. **Skipping the `~/.hermes/goal-prompts/` pre-flight scan and regenerating an artifact that already exists for the same intent.** Pitfall #1 covers the case where the user explicitly points at an existing generated file. The more common and easier-to-miss case is when the user re-issues what *looks* like a fresh generation request (often with new requirements layered on) but a valid artifact pair for the same intent already exists in `~/.hermes/goal-prompts/` from a recent run (minutes-to-hours earlier). Always `ls -la ~/.hermes/goal-prompts/*.md` at the very start of the run and grep titles / `source_prompt_hash` / `# Generated Goal Title` lines for a likely match before deciding regenerate-vs-patch. If a same-intent artifact pair exists and validates, treat the new message as a patch-in-place + scope-extension request: re-run readiness probes (Firecrawl auth, opensrc cache, helper presence, source-claims verifier), patch only the diff the new message introduces (Goal paragraph extension, new In-Scope items, new Acceptance Criteria items, new tasks across all 5 phases with proper RED→GREEN dep wiring, hard_invariants additions), then re-run both validators. Do NOT bump `generated_at` or rotate `source_prompt_hash` on patch — those identify the original intent and remain stable. Filename also stays the same (no `-2` suffix unless a real collision occurs against a different intent). Pitfall #33 already nudges toward this with up-front clarification, but the filesystem scan is the deterministic backstop when clarification didn't run or the user's first message was already exhaustive. When new tasks are added across phases, choose ids in a high-numbered range (e.g. starting at A80/B80/R80/G80/X80) so they don't collide with the helper's auto-generated A00..A06 / R00..R12 / G00..G08 sequence; make every new GREEN task depend directly on the RED ids whose pass-state it needs so the hard_gate stays meaningful.
37. **Finishing an audit execution with an unstaged or dirty final state.** For generated audit goals, final validation must include both unstaged and staged cleanup checks. Run `git diff --check` before staging, stage all intended code/tests/audit evidence, then run `git diff --cached --check` before the squashed commit; audit transcripts frequently contain trailing spaces even when source files are clean. Do not commit in-repo bootstrap virtualenvs such as `.venv-audit`; use a temporary `/tmp` venv for final pytest if system Python lacks pytest/PyYAML, then delete it. If the paired task-list YAML lives outside the repo, make the squashed code/audit commit first, then update only its mutable fields (`status`, `learnings`, `gotchas`) and re-run `scripts/validate_task_list_yaml.py`. See `references/validator-audit-tdd-execution.md`.

38. **Squashed audit commit silently disappears between turns because cron `git pull --ff-only origin main` runs in the skill repo.** When the skill repo has a remote on a Hermes-managed cron (e.g. `srinitude/hermes-goal-prompt-generator`), an unattended `git pull --ff-only origin main` between agent turns can fast-forward HEAD back to the remote tip, dropping any local-only audit commit and reverting tracked files in the worktree. Symptoms: pytest passes once, fails again on the next turn with the exact same RED failures the GREEN edits fixed; `git log --oneline` no longer shows the squashed audit commit, and the worktree shows ALL tracked-file edits as unstaged again; untracked audit/ artifacts survive because they are not in any tracked branch. Recovery: `git reflog | head -20` finds the dangling audit SHA (e.g. `HEAD@{1}: commit (amend): audit: ...`); `git reset --hard <dangling-sha>` restores the tree; if a stash has post-revert evidence, `git stash pop` followed by `git checkout --ours` on the conflicted contract files keeps the audit-commit versions. For new evidence files added after the revert, stage explicitly and `git commit --amend --no-edit`. Do NOT cite literal SHAs in `audit/contradiction-evidence.md` or audit YAML `learnings[]` — every amend rotates the SHA and creates self-referential churn that needs another amend; reference "the squashed audit commit" instead. Push the audit branch up to the remote ONCE the audit is complete to make subsequent pulls no-ops.

39. **`mcp_patch` 1-byte-trailing-newline flake reports failure but the change actually landed on disk.** When patching tracked files in this skill repo, `mcp_patch` (replace mode) sometimes returns `success: false` with `wrote N chars, read back N+1` even though the patch persisted correctly — confirmed by `wc -c` + `grep` on the file. Pitfall #31 covers this for Markdown patches; the same flake hits Python source files. Pre-empt the same-tool-failure loop warning: after the FIRST `mcp_patch` failure, IMMEDIATELY call `mcp_read_file` (or `mcp_execute_code` to read) on the target before retrying. If the new content is present, treat the verifier as a flake and proceed; do not retry `mcp_patch`. For multi-file or multi-anchor changes, default to a single `mcp_execute_code` rewrite pass with explicit `assert old in text` guards — it's faster, sidesteps the flake entirely, and surfaces missing anchors as explicit `AssertionError`s rather than as a verifier loop warning.

40. **Silently keeping the optimistic original claim when the contrarian re-verification probe surfaces a conflict.** The step 11.5 contrarian pass exists precisely because the optimistic validator's `validation_evidence` is sometimes wrong: a Firecrawl `--status` banner can read `Authenticated` while every live HTTP request returns `Connection reset`; an `opensrc` cached repo's `main` SHA can have drifted out from under cited line numbers; a helper-script absolute path can be present on the host filesystem but absent from the executing remote backend; the YAML can declare a `principles[]` id that no task references; structured extraction can be claimed against a missing extract subcommand even though Firecrawl 1.16.0 routes that work through `firecrawl agent`. When a `Conflict` surfaces, **never** retain the original optimistic phrasing in `validation_evidence`. Reconcile the YAML through one of the deterministic resolutions (`kept_original` is reserved for true `info`-severity matches, NOT for inconvenient `warn`/`error` conflicts): rewrite the affected entry to `attempted` (`downgraded_to_attempted`), to `unavailable` (`downgraded_to_unavailable`), to a corrected literal (`corrected_in_yaml`), or escalate it to `execution_time_required` (`escalated_as_execution_time_required`) and let `final_state` record `some-claims-escalated-to-execution-time`. A correctly-escalated `final_state` is a legitimate generator outcome; a silently-retained false claim is a contract violation that the structural validator will refuse on the next run. See `references/contrarian-validation.md` for the full decision tree, the standalone `python3 scripts/run_contrarian_validation.py [--dry-run] [--strict] <tdd-yaml>...` entry point, and the four canonical failure modes the contrarian pass MUST probe.

41. **Repeating an invalid `claude` prompt flag after the user or CLI has shown the correct syntax.** Generated-goal execution often involves a persisted Coding Agent Execution Contract, but the runtime command still has to match the installed `claude` binary. Probe `claude --help` before the first invocation. The official long form of the prompt-mode flag is `--print` (short `-p`); the pre-1.6.1 contract literal `--p` is rejected by the binary with `error: unknown option '--p'`. The prompt payload is a positional argument, not the value of `--print` — write `claude --print "<instructions>"` (or `claude -p "<instructions>"`), never `claude --p "<instructions>"`. Keep `--output-format stream-json` and `--input-format stream-json` for structured IO. If a stale contract or old reference still says `--p`, update the contract literal to `--print`, record the mismatch in the task ledger's mutable `learnings`/`gotchas`, and resume the strict ANALYSIS → BOOTSTRAP → RED → GREEN → REFACTOR walk instead of asking the user again. If the full flag set hangs and the user explicitly says not to worry about flags for now, treat that as a narrow runtime waiver: record it in mutable YAML fields, keep TDD/hard-gate discipline, and continue through the repo's real command boundary instead of stalling on Claude flag purity. See `references/claude-cli-execution-syntax.md`.

43. **Stuffing descriptive notes into `validation_evidence.opensrc.fetched[<slug>].key_paths[]` and getting the entire `validation_reconciliation` block silently overwritten by the contrarian pass.** `scripts/run_contrarian_validation.py::_replay_opensrc` calls `Path(kp).exists()` on every key_paths entry. Strings like `"opensrc list --json schema: {updatedAt, ...}"` or `"opensrc fetch --help (signature: ...)"` always fail that check, get escalated as `opensrc_path_exists` / `escalated_as_execution_time_required` with severity `error`, and overwrite any honest `info` / `warn` reconciliation entries you wrote at generation time — flipping `final_state` to `some-claims-escalated-to-execution-time`. Fix: keep `key_paths[]` strictly for real on-disk paths (the binary at `/opt/homebrew/bin/opensrc`, the inventory at `~/.opensrc/sources.json`, the cache root at `~/.opensrc/repos`); move help-text / schema / signature observations into a sibling field the contrarian pass does not probe (`signatures_observed`, `rationale`, `evidence`). After the rewrite the contrarian pass returns `all-claims-reconciled`; you can then re-merge your generation-time honest reconciliation entries (with their correct severities) by writing the `validation_reconciliation` block yourself — the structural validator does not require the contrarian pass to be the last writer. See `references/contrarian-validation.md` §"`opensrc.fetched[<slug>].key_paths` MUST be real on-disk paths".

    **Generalization (May 2026):** the same write-back behavior applies to ALL generation-time reconciliation entries, not just the opensrc-paths case. When you've manually corrected helper-baseline claims during generation (auth, task counts, opensrc.fetched, repository_context.key_paths, etc.), running `python3 scripts/run_contrarian_validation.py <yaml>` (write-back, not `--dry-run`) finds 0 live conflicts and **clobbers your historical conflicts/resolutions to empty arrays**. Workflow that survives: (a) build YAML with historical reconciliation entries from a Python dict and stage to `/tmp/<slug>-final.json`; (b) write YAML and run structural validator; (c) run `--dry-run` to confirm 0 live conflicts; (d) skip write-back, OR re-merge staged historical entries afterward and add a top-level `note:` explaining the override. Re-running structural validator after the merge MUST stay green. Pitfall #40's "never silently retain optimistic claims" rule still applies — it governs NEW live conflicts, not historical reconciled evidence.

45. **Trying to shell-quote a real goal prompt through `terminal(command="... fish -lc 'python3 ... --json \"<prompt>\"'")`.** Real prompts contain parens, single and double quotes, backslashes, asterisks, angle brackets, and embedded multi-line bullets, and the wrapping `bash -c` / `fish -lc` `eval` chokes on the unescaped parens before the helper ever runs (`bash: eval: line N: syntax error near unexpected token '('`). Don't escape-by-hand; bypass the wrapping shell. Use `mcp_execute_code` + `subprocess.run(["python3", helper, "--workdir", repo, "--json", prompt], env=os.environ.copy(), timeout=600)`. The argv list goes through `execvp` with zero shell parsing, so parens/quotes/backslashes/multi-line content all pass through verbatim, and `env=os.environ.copy()` keeps `FIRECRAWL_API_KEY` and other helper-required env vars. Heuristic: if the prompt is more than ~3 lines or contains any of `()` `'"` `\` `*` `<` `>`, do not attempt to shell-quote it. See `references/shell-escape-when-passing-prompts-to-helper.md`.

46. **Hand-authoring `coding_agent_execution_contract.worktree_directory` with the wrong field names and burning a validator round-trip.** The structural validator (`scripts/validate_task_list_yaml.py`) requires the literal keys `flag` (must equal `"--worktree"`), `short_flag` (must equal `"-w"`), `root` (non-empty string), `directory_template` (must contain the substring `.claude/worktrees/<worktree-name>`), and `resolution_rule` (non-empty string). It does NOT accept `flag_long`, `flag_short`, `rule`, or any other near-miss. The same five keys are required on `validation_evidence.repository_context.claude_worktree`. The SKILL.md describes the block in prose ("maps `--worktree` / `-w` to `.claude/worktrees/<worktree-name>` inside the active Hermes worktree") which is easy to translate into the wrong field names. Canonical shape:
    ```yaml
    coding_agent_execution_contract:
      worktree_directory:
        flag: "--worktree"
        short_flag: "-w"
        root: "<repo_root>/.claude/worktrees"
        directory_template: "<repo_root>/.claude/worktrees/<worktree-name>"
        resolution_rule: "When --worktree <worktree-name> is supplied, resolve ..."
    validation_evidence:
      repository_context:
        claude_worktree:
          flag: "--worktree"
          short_flag: "-w"
          root: "<repo_root>/.claude/worktrees"
          directory_template: "<repo_root>/.claude/worktrees/<worktree-name>"
    ```
    When you hand-write the YAML (e.g. the programmatic-rebuild path in pitfall #36), copy these five keys verbatim. If the validator fails with `FAIL: coding_agent_execution_contract.worktree_directory.<key>: ...`, the fix is always renaming/adding the literal key, not synthesizing the value differently.

47. **Trusting the helper's empty `validation_evidence.opensrc.fetched: {}` baseline when the spec names specific OSS repos.** The generator helper (`generate_goal_prompt.py`) probes `opensrc` for readiness but does NOT know which repos the goal depends on, so it ships the baseline YAML with `opensrc.fetched: {}` and a generic divergence note even when opensrc is fully available locally and the user-named repos are cached. The structural validator does not require `fetched` to be populated, so this slips through quietly — but the contract is incomplete: every spec-named OSS repo MUST have its own entry under `fetched[<org>/<repo>].key_paths[]` with real on-disk absolute paths (per pitfall #43). Always replace the helper's empty baseline yourself: run `opensrc list` to confirm the cache, run `Path(p).exists()` on every cited path before writing the YAML, and populate `fetched[<slug>] = {branch, path, cache_busted, key_paths[], rationale}`. Treat the helper's emitted opensrc block as a placeholder, not as evidence.

    **Symmetric over-collection on Firecrawl maps (May 2026):** the SAME "trust the helper, lose context" failure mode hits `validation_evidence.firecrawl.required_maps_present` from the OPPOSITE direction — the helper dumps EVERY cached URL map (`bun`, `daytona`, `flora-app`, `mcp-spec`, `python-stdlib`, `playwright-docs`, etc., often 70+ entries) into `required_maps_present` with `map_command: "cache-inspected; refresh with firecrawl map ..."` regardless of whether those docs are relevant to THIS goal. The structural validator accepts the noise (positive `url_count`s) but a downstream agent cannot tell authoritative-for-this-goal from background cache pollution. Trim `required_maps_present` to ONLY the techs named in the spec (typically 3-8 maps), and re-run live `firecrawl map --json --pretty --limit 5000 <docs-root>` for any stale or missing ones. Same fix shape as the opensrc case: helper emission is a placeholder, replace before writing. Also applies to the case-insensitive `repository_context.key_paths` problem in pitfall #52.

48. **`validation_reconciliation.resolutions` is checked for LITERAL list equality with `conflicts`, not just key-shape mirroring.** `validate_task_list_yaml.py` line ~156 does `if buckets["resolutions"] != buckets["conflicts"]: problems.append("validation_reconciliation.resolutions: must preserve conflicts ordering")`. That is a Python `==` on two list-of-dicts. Adding extra keys to resolutions entries (like `action: "..."`) makes resolutions diverge from conflicts and fails. The fix that survives every run: write `conflicts[]` with the canonical six fields (`check_id`, `evidence_target`, `original_claim`, `contrarian_observation`, `severity`, `resolution`), then `resolutions = copy.deepcopy(conflicts)`. If you need to record the literal action you took, embed it in the `resolution` enum value itself (`corrected_in_yaml`, `downgraded_to_attempted`, `escalated_as_execution_time_required`, etc.) — do NOT add a sibling `action` key. The `note:` top-level inside `validation_reconciliation` is the right place for free-form prose like "we replaced the helper baseline with live evidence."

49. **GREEN tasks must reference at least one RED task in `dependencies` DIRECTLY — transitive RED dependency through other GREEN tasks fails the validator.** When you build aggregator GREEN tasks (e.g. `G09: run the parity matrix harness against every cell`, `G10: surface the new status command`, `G11: structured telemetry on every plugin call`), the natural shape is to depend only on the GREEN tasks that produced the data. The validator (`validate_task_list_yaml.py`'s `_check_phase_ordering` family) walks each GREEN task's `dependencies` looking for a literal `R0n` id — it does NOT recurse through the GREEN deps. Add at least one RED id to every aggregator task's `dependencies` list, even if it feels redundant. Heuristic: pick the RED test whose pass-state is necessary for the aggregator to be meaningful (parity-matrix aggregator → all R01..R11; telemetry aggregator → R02 + R07 + R11; status-surface aggregator → R04 + R05). The validator error is the explicit `FAIL: G0X: GREEN task must reference >=1 RED task in dependencies`.

50. **Validator demands every declared principle id appears in at least one task's `principle_ids`.** When the helper-emitted baseline has 18 principles in `principles{}` and the rebuilt phases only naturally reference 15, the structural validator fails with `principles: unused ids [...]` — even if the missing ids are valid software-engineering principles you simply didn't wire. Three options, in order of preference: (a) wire each orphan into existing tasks where it actually fits (P4 "preserve failure causes" → telemetry/circuit-breaker tasks; P15 "cache deliberately" → semantic-recall + parity-harness tasks; P16 "serialize shared-state updates" → bounded-queue + index-write tasks); (b) add a small task that explicitly validates that principle if it's important enough to keep; (c) remove the unused id from `principles{}` and the SKILL.md (last resort — only if the principle truly does not apply). The skill body lists 18 canonical principles for a reason; option (a) is almost always right. See `references/principle-id-wiring-and-evidence-construction.md` for the canonical P1..P18 → task-family mapping table plus the positive-construction (build, don't trim) pattern for `firecrawl.required_maps_present` and `opensrc.fetched`.

    **Companion gotcha (May 2026 patch run): `principle_ids` MUST match the actual top-level `principles{}` keys verbatim — and the helper baseline emits BARE ids like `P1`, `P2`, ..., `P18`, NOT descriptive slugs like `P1_descriptions_before_execution`.** Several skill references (including `references/coding-agent-task-list-yaml.md`) show example slug-shaped ids, which makes it tempting to invent the slug form when hand-authoring scope-extension tasks for an existing YAML. The validator does a literal `set(task.principle_ids) <= set(principles.keys())` check; every slug-shaped id fails as `bad principle_ids ref 'P10_data_validation_at_boundaries'` etc., and the failure cascades across all new tasks (33 FAILs in one observed run). ALWAYS probe `principles.keys()` on the existing YAML before writing scope-extension tasks: `python3 -c "import yaml; print(list(yaml.safe_load(open('<path>.yaml')).get('principles',{}).keys()))"`. If the baseline uses bare ids, use bare ids. If the baseline uses slugs, use slugs. Don't mix shapes — and don't trust the reference doc's example shape to match what the live helper emitted for THIS YAML. This is a one-cell fix (`{slug: bare for slug,bare in remap.items()}` over each new task) — pre-empt it by probing first.

51. **`metadata.hard_invariants` shape is per-YAML — list OR dict — and patch code MUST probe before extending it.** The helper baseline can emit `metadata.hard_invariants` as either a Python `list` of strings (`["screenshot_required_per_alteration: true", ...]`) or a `dict` (`{"screenshot_required_per_alteration": true, ...}`) depending on the goal Markdown's hard-invariants block shape. The structural validator accepts both. Patch code that does `data['metadata']['hard_invariants'][:3]` to "peek at the first three" hits `TypeError: unhashable type: 'slice'` against the dict shape (it tries to subscript with a `slice` object); patch code that calls `.append(new_rule)` against the dict shape hits `AttributeError: 'dict' object has no attribute 'append'`. Always probe the type FIRST: `hi = data['metadata']['hard_invariants']; print(type(hi).__name__, list(hi.keys()) if isinstance(hi, dict) else hi[:3] if isinstance(hi, list) else hi)`. Then branch — `hi[<key>] = <value>` for dict, `hi.append(<rule>)` for list. The same shape ambiguity applies to a few other helper-baseline blocks; probe before mutating any helper-emitted structure that the SKILL.md describes only by example shape.

52. **Helper baseline `repository_context.key_paths` includes case-collision phantoms on macOS and misses operative files.** `repository_evidence(workdir)` walks a fixed list of agent-context filename candidates and reports each that resolves on disk. On macOS's case-insensitive APFS / HFS+, a single `README.md` resolves to `README.md`, `Readme.md`, AND `readme.md` because each `Path.exists()` returns `True` against the same inode — phantoms propagate into every task's `context_files`. Meanwhile the OPERATIVE files for the goal (e.g. `skills/<name>/SKILL.md` for a skills.sh-shaped goal, `.github/scripts/validate_skill.py`, the script being patched) get pushed off the bottom of the 24-entry priority cap. Diagnostic: a `key_paths[]` containing both `README.md` and `Readme.md`/`readme.md` AND the actual most-edited file isn't there. Fix: rebuild yourself before writing — collapse case-insensitive duplicates via `os.path.realpath` + `str.lower()` dedup, then explicitly seed the operative files for THIS goal. The contrarian pass's `recheck_repository_key_path` only catches *vanished* paths, NOT phantoms or omissions, so the structural validator passes and the noise propagates. Same fix shape as #44, #47: treat helper's repository-context as a placeholder, reconcile against reality, record the rebuild in `validation_reconciliation` with severity `warn` and resolution `corrected_in_yaml`.

53. **Debugging skills.sh / `npx skills add` failures from a third-party SKILL.md repo (e.g. "No valid skills found. 44. **Skipping the repository-context exploration pass and shipping a goal contract whose `context_files` reference paths that don't exist in the invoking workdir.** Pre-1.6.0 generations only validated docs (Firecrawl) and OSS deps (`opensrc`); the workdir was assumed to be fine. The contrarian pass (`recheck_repository_key_path`) re-checks every promised key path on disk and downgrades vanished entries to `downgraded_to_attempted` in `validation_reconciliation`; treat that conflict as a real signal that the workdir was retargeted or the snapshot is stale, not as noise to suppress. Never edit the Markdown's `## Repository Context` section to invent a path that does not exist on disk; if the workdir is genuinely sparse, let the snapshot reflect that and add a BOOTSTRAP/ANALYSIS task to discover canonical layout before any GREEN edit.
